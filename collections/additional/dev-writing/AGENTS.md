# Developer Writing

## Write The Way A Person Types

Text published under a person's name reads as though a person typed it. Use contractions, plain everyday words, and one idea per sentence; let the occasional fragment stand instead of polishing every clause to the same weight. No emoji, no exclamation marks, no bulleted list where a sentence would do, and none of the stock vocabulary that reads generated (crucial, robust, leverage, seamless, comprehensive, streamline, enhance, additionally). Brevity is tone, not permission to drop what the message has to carry.

## No Dashes And No Forced Contrast

Never use an em or en dash as a connector; use a comma, a period, or a line break. Never frame a point as "not X but Y" when nobody raised X — the negative half only adds weight, so state the point directly. A contrast whose two halves both carry information stays.

## Stop At The Last Point

End when the substance ends. No wrap-up sentence, no reassurance, no closing counterfactual ("hope that helps", "that should be enough"). A final line that carries the ask, the verdict, or the reason the ask exists stays, because it is content rather than a sign-off.

## Name Things The Way People Do

Use the name a reader would use: the feature, the error message, the file, the endpoint. Never an internal enum value or identifier when the reader knows the thing by another name. Where the raw identifier is the point, keep it exactly and wrap it in backticks where they render.

## Never Invent An Event

Do not state or imply a meeting, a discussion, a decision, or anything else the reader did not see or hear about. Your own work is the person's work, so "I checked it" is fine; describing how you checked, when nobody asked, is not. Do not attribute your reasoning to the team.
