## Purpose

Once a service is running on a live host, "the build passed" is not the same claim as "the host is serving the change". This skill is the discipline for iterating against a live box without breaking it: read the live state before touching it, ship one small change at a time through a gate, deploy in an order that respects schema changes, and prove from the outside that what users get is what you pushed — with a rollback you already know how to run.

## When to use it

When an app is already deployed to a live host (VPS, home server, single box) and each change needs to be seen there: hotfixing a live bug, validating a config or dependency change, iterating on a self-hosted service, or confirming that something already merged is actually what users receive. Not for provisioning a new environment (that is infrastructure as code) and not for authoring the pipeline that deploys (that is pipeline design).

## Steps / checklist

1. **Read the live state first, and change nothing.** Before any mutation, establish the baseline: what is running, at which commit, and whether it is healthy. Something like `ssh <host> 'cd <app-dir> && docker compose ps'`, `ssh <host> 'cd <app-dir> && docker compose logs --tail=100 <service>'`, a probe of the service address (`ssh <host> 'cd <app-dir> && curl -fsS http://<service-address>:<port>/health'`), and the host's git state (`ssh <host> 'git -C <app-dir> log --oneline -3 && git -C <app-dir> status --short'`). Record the current branch, commit/tag, and health result. This phase is strictly read-only — no restarts, no `compose up`, no image or volume pruning, no file edits — because the baseline is both your "before" fact and your rollback target. If the host is already unhealthy, say so before deploying: you would otherwise blame your change for a pre-existing failure.
2. **Make the smallest change that addresses the issue.** One change per deploy. Bundle a refactor or a "while I'm here" fix and a failing deploy no longer tells you what to revert. If the fix needs three unrelated edits, ship the first one and re-enter the loop.
3. **Pass the local gate.** Run the project's own gate — tests, lint, and build — before anything leaves the machine. A red gate stops here; no deploy is worth skipping it. If the gate cannot run locally, run it in CI and wait for green rather than deploying on a hunch.
4. **Push the fix; never hand-patch the host.** Commit and push. Editing files under `<app-dir>` on the host is not a shortcut: the next pull conflicts or silently reverts the patch, and the fix exists nowhere but that box. The host runs the repository, or it runs something nobody can reproduce.
5. **Show the plan, get approval, then deploy in a migration-safe order.** This is a live-host mutation, so state the diff, the exact commands, the commit being deployed, and the rollback point from step 1, then wait for an explicit human yes in the current conversation before running anything — the same bar as any other deploy or apply. Once approved, a change that includes a schema migration must not let the new code serve traffic against the old schema. Split the deploy rather than hoping: pull and build (`ssh <host> 'cd <app-dir> && git pull --ff-only && docker compose build <service>'`), run the migration (`ssh <host> 'cd <app-dir> && docker compose run --rm <service> <migrate-command>'`), then start the new version (`ssh <host> 'cd <app-dir> && docker compose up -d <service>'`). If the migration and the code cannot be ordered that way — a long migration, or old and new instances overlapping during a rolling restart — say so explicitly, describe the error window, and use expand/contract: ship an additive migration the old code tolerates, deploy code that handles both shapes, and only then remove the old shape. Never let a reader discover the window from an incident report.
6. **Verify the served artifact, not the local build.** A green gate proves the code compiles; only the host proves it is what users get. Check all four: the container is actually up and not restarting (`docker compose ps`), a real route answers (`curl -fsS http://<service-address>:<port>/health` plus at least one route that exercises the change), the running version matches what you pushed (image tag, commit, or a version endpoint), and a before/after fact changed — the served bundle contains the new string (`curl -fsS http://<service-address>:<port>/<asset-path> | grep -F '<expected-marker>'`), the new log line appears once, the previously failing request now returns the expected status. "Looks fine in the browser" is not verification; a cached asset can serve yesterday's code from a host that is perfectly healthy.
7. **On failure, read the evidence — then decide fix-forward or roll back.** Read the actual error from `docker compose logs --tail=100 <service>` before changing anything else. Fix forward only while the service is up and the next step is clear; if it is not obvious within a couple of iterations, roll back to the last known-good tag or commit and debug from a working baseline. Never leave the service down "while you investigate": a stale but serving deployment beats a clever fix on a dead host.
8. **Roll back along the same path you deployed.** Keep the last known-good tag or commit and the deploy branch recorded from step 1, and roll back on that branch — a plain `git checkout <last-good-tag>` leaves a detached HEAD, and the next `git pull --ff-only` fails, so the loop can't be re-entered. Use `git fetch --tags && git checkout <deploy-branch> && git reset --hard <last-good-tag>`, then `docker compose up --build -d <service>`. The host should have no local edits (step 4), so the hard reset discards nothing worth keeping; if it would, stop — local edits on the host are the bug. Then re-run step 6 against the restored version. If the bad deploy carried a migration, state plainly whether it was reversed and, if not, whether the old code tolerates the newer schema. A rollback that leaves the schema ahead of the code is a second incident waiting for the next restart.
9. **Freeze the network plane.** An unrelated deploy changes application code and nothing else. Do not touch reverse-proxy configuration, published ports, compose network membership, or `.env`/secret files in the same deploy — not to "quickly fix" a 502, not as a drive-by tidy-up. Those are separate, planned changes with their own verification, because a mistaken port or proxy route takes down far more than the service you were editing and cannot be reasoned about from the app's logs. If the change genuinely needs one of them, stop, state the change and its rollback, and get it treated as its own step.
10. **Record the facts where the next person will look.** Leave the deploy note in the PR, the handoff, or the memory system: what changed, the local gate result, the commit, the host, container state, health and artifact proof, and the rollback point. "Deployed" without those facts is a claim, not a record.

## Expected output

A live host that serves exactly the commit you pushed, proven by an outside-the-container check rather than an assertion, reachable at every point during the deploy or restored from a named rollback point. If a reviewer cannot tell from your notes which commit is live, what you checked, and what to run to undo it, the deploy isn't done.
