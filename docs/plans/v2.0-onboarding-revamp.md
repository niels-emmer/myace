# MyACE v2.0 — Onboarding & Usage Revamp

Status: **Phases 1–5 implemented.** The v2.0 pre-release version bump is
owned by the integration PR, not by Phase 5.
Source: accepted design proposal (`onboarding-usage-flow.md`, design
workstream), adapted here into a repo build plan.

## Why

MyACE's data model is object-first: Collections, Profiles, Artifacts. That is
accurate for the API and the compiler, but it is the wrong shape for a first
visit. A new user sees a dashboard of object counts, must infer that a
"Profile" is a recipe, and has to learn three nouns before doing anything
useful. The revamp keeps the internals exactly as they are and changes the
presentation to one repeated story:

```
Browse packs  →  Build a setup  →  Install to your frameworks  →  (optionally) Publish
```

## Vocabulary (presentation only)

| User-facing | Internal (unchanged) | Meaning |
|---|---|---|
| **Pack** | `Collection` | A bundle of rules, skills, agents, and workflows around a role or capability. |
| **Bundle** | *(curated constant)* | A recommended starting combination. Not a table; `frontend/src/lib/bundles.ts`. |
| **Setup** | `Profile` | A named recipe: a starting-point pack + add-ons + item toggles, targeting one or more frameworks. |
| **Install** | compile + pull/apply | Writing a setup's output to a framework. |
| **Item** | `Artifact` | One rule, skill, agent, workflow, or model config. |
| **Pipeline** | orchestration gallery / `handoff_to` graph | Agents plus their handoff routes; a tab inside Packs. |

Pack kinds stay the existing `collection_type`: **Starting point** =
`base`, **Add-on** = `additional`. Source badges are derived, not stored:
**Starter** (`is_starter_pack`), **Mine** (`owner_id` = current user), or
**Community** (everything else visible).

API routes, SQLModel models, compiler functions, and tests keep
`collection`, `profile`, `artifact`, and `compile`. See `AGENTS.md` rule 42.

## Information architecture

```
Home                     /
Setups                   /setups
  └ /setups/:id
  └ /setups/:id/install
Packs                    /packs
  ├ Browse packs         /packs
  ├ My packs             /packs/mine
  ├ Pipelines            /packs/pipelines
  │   └ new              /packs/pipelines/new
  ├ Import packs         /packs/import
  ├ Pack detail          /packs/:id        (owned, starter, and community)
  │   ├ publish          /packs/:id/publish
  │   ├ manage (owner)   /packs/:id/manage
  │   └ new item         /packs/:id/items/new
  └ community detail     /packs/community/:id → redirects to /packs/:id
Settings                 /settings
  ├ Account              /settings/account
  ├ Moderation†          /settings/moderation
  └ System†              /settings/system
```

Outside the four areas: **My machine** (`/machine`) is a secondary sidebar
footer link with tabs **Overview** (companion health + detected
frameworks), **Audit**, and **Sync**. The **⌘K command palette** is global.
† role-gated exactly as before (`RequireModerator` / `RequireAdmin`).

Every pre-revamp path redirects (param-preserving where needed) — the full
map lives in `frontend/src/App.tsx` and is covered by
`frontend/src/App.routes.test.tsx`. `/welcome` was rebuilt as the public
storefront in Phase 5.

## Screens in Phase 1

### Home (`/`)

- One state banner derived from `GET /profiles` + `GET /sync/status`:
  no setups → *Build your first setup*; setups but no sync rows → *Your
  setup is ready — install it*; any drift row → amber *N changes since
  install*; otherwise a quiet healthy line.
- Setup cards: name, pack names, one chip per target
  (`target_frameworks`, falling back to `target_framework`) with status
  verified / changed / not verified / not installed, plus a New setup card.
- Recommended packs: four cards from the starter `base` collections, using
  the `BUNDLES` constant for display names/descriptions/membership.
- Community highlights: four cards from `GET /collections/community`.
- Footer: `N frameworks supported · MyACE vX · source` — no object counts.

### Packs library (`/packs`)

Search (name/description/category), facets **All / Starting points /
Add-ons / Mine / Community**, category chips from
`GET /collections/community/categories`, sort **Recommended / Highest rated /
Recently updated** (no "Most used" — the use counter is advisory), a
"Start here" bundle strip, and per-filter empty states with Create/Import
actions. Every card links to the unified `/packs/:id`. Phase 5 made this page
public: anonymous visitors get the public storefront reads plus a read-only
view (no Mine facet, no Create/Import), and sign-up CTAs. Phase 2's parallel
work should preserve that anonymous branch when it touches this page.

### Command palette (⌘K)

Actions (New setup, Import packs, Check my machine, Publish a pack), pages
(Home, Setups, Packs, Pipelines, My machine, Settings), then up to five
cached packs and five cached setups. Keyboard-first (↑/↓, Enter, Escape,
Tab trapped in the search field), `role="dialog"` + `role="listbox"`, and
click-outside close. No new backend: it reuses the existing `['collections']`
and `['profiles']` query keys.

## Data model work (later phases)

- **Phase 3:** add `Profile.target_frameworks` (JSON text, default `"[]"`,
  backfilled from `target_framework`; legacy column retained). Phase 1's
  frontend already reads it optionally and falls back.
- **Phase 2:** `User.onboarding_completed_at`, set when the first-run
  wizard finishes or is skipped.
- **Phase 3:** pack freezing/reference snapshots and use counts. *(Shipped —
  migration `e3f4a5b6c7d8`, ADR-0015.)*
- **Phase 5:** `Collection.license` and public storefront work. *(The `license`
  column shipped with Phase 3's migration; Phase 5 surfaces it in the publish
  wizard and pack detail. Public reads are in ADR-0014.)*

## Build order

Each phase is a separate branch/PR, independently shippable.

1. **Phase 1 — Vocabulary, navigation, Home, ⌘K** — *shipped*. Four-area
   sidebar, 52px top bar with breadcrumbs and search, new Home, Packs library
   shell, tabbed My machine, route map + redirects, command palette, docs and
   tests.
2. **Phase 2 — First-run wizard + import branch** — *in progress on a
   parallel branch* (frontend only, ends in zip/CLI). `/onboarding` five
   steps, resume/skip, `onboarding_completed_at`. Home's "Build your first
   setup" CTA moves from `/setups` to `/onboarding`.
3. **Phase 3 — Multi-framework setups, snapshots, use counts, publish
   status** — *shipped*. `target_frameworks`, frozen pack references,
   download counters, moderation status surfaced on setup cards, `license`.
4. **Phase 4 — Companion `/apply`** — *shipped* (ADR-0016). Local install
   execution through `myace serve`.
5. **Phase 5 — Public storefront + publish polish** — *this PR*. Rebuilt
   `/welcome` (featured packs, four-step story, framework strip), public
   `/packs` browsing (ADR-0014), unified `/packs/:id` detail with
   ratings/comments for owned and community packs, four-step publish wizard
   and status tracker, corrected README captions and structure. No new
   screenshots were taken; the storefront is described rather than pictured.

## Versioning decision

This series targets a **v2.0 pre-release**. All three packages
(`backend/`, `cli/`, `frontend/`) stayed at **1.12.0** on the phase branches
so intermediate deployments remained on the current minor line. The
**integration PR** applied **`2.0.0-pre.1`** once across all three packages
and added `CHANGELOG.md`. The work is additive and backward-compatible
(frontend presentation first, then additive API fields with legacy
fallbacks). Never bump a single package outside an integration/release PR.

## Risks

- Copy churn touches many tests. Mitigate by asserting roles/headings and
  redirect destinations rather than marketing strings.
- The redirect map is the compatibility contract for bookmarks and the
  CLI's docs; `App.routes.test.tsx` must stay exhaustive.
- Starter-pack content edits still do not reach an already-seeded
  deployment (AGENTS.md rule 25) — unrelated to this revamp, but relevant
  when Phase 5 changes starter descriptions.

## Phase 1 limitations (deliberate)

- `/setups` is the existing setup composer/list; the guided wizard and
  onboarding flag are Phase 2.
- "Publish a pack" and pack-detail actions open the existing pages;
  the publish wizard, unified community detail, and install/apply UI land
  in Phases 3–5.
- Home's catalog and recommendation copy comes from the current starter
  set; nothing here freezes or version-pins a referenced pack.

## Known follow-ups (recorded, not fixed in the integration PR)

1. **AddToSetup adapter filtering.** `components/AddToSetup.tsx` derives a
   pack's frameworks from `target_compatibility` without intersecting with
   the currently enabled adapters. A pack that declares an admin-disabled
   adapter can add that target to a new setup, and compiling it then fails
   with `AdapterDisabledError`. The fix is a `GET /adapters` lookup in
   `AddToSetup` before writing `target_frameworks`.
2. **`packApi.usePack` is dead code.** The UI posts the advisory use counter
   alongside attach; the exported helper is no longer called. Remove it or
   reuse it when a non-attaching "use" surface returns.
3. **Starter-pack content refresh.** Editing an already-seeded starter pack
   still does not reach an existing deployment (AGENTS.md rule 25). Unrelated
   to the revamp, but relevant when starter descriptions or contents change.
